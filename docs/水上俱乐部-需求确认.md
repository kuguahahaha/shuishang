### 2.3 输出项

| 输出项 | 公式 | 形式 |
|---|---|---|
| 筹码总值 | Σ（数量 × 面额） | 只读，加粗高亮 |
| 积分 | 筹码总值 ÷ 2000 | 只读，保留 2 位小数（四舍五入） |
| 积分·向上取整 | `Math.ceil(积分)` | 只读 |
| 积分·向下取整 | `Math.floor(积分)` | 只读 |
| 手数 | 用户填写 | **可输入**，整数 |
| 最终积分（决算） | 取整积分 − 手数 × 10 | 只读，重点高亮 |

### 2.4 计算公式

```
筹码总值 = 100000×a + 50000×b + 10000×c + 5000×d + 1000×e + 500×f + 100×g
积分     = 筹码总值 ÷ 2000
积分(上) = ceil(积分)
积分(下) = floor(积分)
1 手     = 20000 筹码 = 10 积分
最终积分 = 取整积分 − 手数 × 10        （等价于 (筹码总值 − 手数×20000) ÷ 2000 再取整）
```

因为 20000 ÷ 2000 = 10 恰好是整数，所以「先扣筹码再算积分」和「先算积分再扣手数」结果完全一致，两种算法不用纠结。

### 2.5 手数输入规则（你的补充已记录）

- 允许 **正整数 / 负整数 / 0**
- **必须是整数**，输入小数（如 1.5）→ 输入框标红 + 提示「手数必须为整数」，并且**不参与计算**（该项显示 `—`）
- 不做上下限限制
- 手数为负 = 反向抵扣（比如退手、退还买入手数）

> 各面额的「数量」输入框我建议限制为 **≥0 的整数**（筹码个数不可能为负）。见待确认 #5。

### 2.6 数值示例（用于验收）

输入：黑×10、粉×1、紫×3、蓝×5、绿×2

```
筹码总值 = 10×10000 + 1×5000 + 3×1000 + 5×500 + 2×100
        = 100000 + 5000 + 3000 + 2500 + 200 = 110,700
积分     = 110700 ÷ 2000 = 55.35
积分(上) = 56
积分(下) = 55
手数 = 2  → 扣 2×10 = 20 积分
最终积分(上) = 36     最终积分(下) = 35
手数 = -1 → 加 10 积分
最终积分(上) = 66     最终积分(下) = 65
```

## 三、交互规则（我的设计，待确认 #3）

| 行为 | 处理 |
|---|---|
| 输入任一筹码数量 | 实时重算：总值 → 积分 → 上/下取整 → 最终积分 |
| 输入手数 | 只影响「最终积分」，不影响总值/积分 |
| 手数填非整数 | 标红提示，最终积分显示 `—` |
| Enter 键 | 同原工具，快捷触发计算 |
| 重置所有 | 一并清空本模块所有输入输出 |
| **与货币区联动** | **不联动**（本模块不写 CNY/USD/BB） |
| **与另两套筹码互斥** | **不互斥**（三套独立，各算各的） |

理由：水上俱乐部是「积分结算」场景，和汇率换算无关，独立最不容易算错账。
