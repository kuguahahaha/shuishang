## 二、角色与权限模型（新增）

### 2.1 三种角色的职责边界

| 角色 | 身份来源 | 权限 | 典型动作 |
|---|---|---|---|
| **管理员** | 角色表指定 | 全部权限 | 建场次、指定记录人、增删桌号、维护昵称字典、改/删任何记录、分配角色、导出、标记对账 |
| **记录人员** | 角色表指定 + **场次归属** | 只能写自己负责的场次 | 录入/修改本场记录、签到、提交本场数据、结束本场 |
| **对账员** | 角色表指定 | **只读 + 导出** | 查看各场记录与排名、导出 Excel、核对账目、标记「已对账」 |

> **关键设计**：记录人员是「**场次级**」权限——同一个管理员可以当 A 场的记录员、B 场请别人当记录员。写权限校验按「当前用户是否被指派为该场次的记录人」来判断，而不是全局角色一刀切。

### 2.2 身份识别怎么落地（关键决策点）

纯静态网页 + 云函数架构下，**"你是谁"必须能被云函数验证**，否则权限形同虚设。三种做法：

| 方案 | 做法 | 安全性 | 开发量 | 体验 | 建议 |
|---|---|---|---|---|---|
| **B-1 昵称+角色选择**（推荐起步） | 进入页面时选「昵称 + 角色」，云函数按角色表校验该昵称是否有此角色、是否负责该场次 | ⚠️ 可冒名（熟人局影响小） | 0.5 人天 | 输入 2 个字段即可 | ✅ 先做这个 |
| **A 飞书 OAuth 登录** | 网页跳飞书授权，拿 open_id，云函数据此映射角色 | ✅ 高 | +1.5 人天 | 首次授权有跳转 | 后期升级路径 |
| **C 纯靠飞书表格原生权限** | 网页不鉴权，能编辑表格的人自然有写权 | ⚠️ 粗粒度，做不到「只改自己那场」 | 0 | 无感 | 只能配合 B-1 用作第二层防线 |

**推荐组合**：**B-1 为主 + 飞书原生权限做兜底**
- 飞书侧把管理员设为表格管理员，**对账员只给「可阅读」权限**（飞书原生，天然只读，截图泄露也改不了数据）
- 记录人员给「可编辑」但云函数侧再校验「只能写自己负责的场次」
- 以后想更严谨再叠加 A（飞书 OAuth），角色表加一列 open_id 即可平滑升级

### 2.3 场次生命周期（状态机）

```
       管理员建场次
            ↓
      ┌──────────┐  记录人员开始录入
      │ 未开始   │──────────────┐
      └──────────┘              ↓
                          ┌──────────┐  记录人员点「结束本场」
                          │  进行中   │──────────────┐
                          └──────────┘              ↓
        管理员/记录人员可改 ←──┌──────────┐   ┌──────────┐
              ↑               │  已结束   │   │  已对账   │
              └───────────────┴──────────┘   └──────────┘
                管理员解锁重开                 对账员标记
```

| 状态 | 谁能改数据 | 说明 |
|---|---|---|
| 未开始 | 管理员 | 场次已建，尚未录入 |
| 进行中 | 该场记录人员（可改自己的）+ 管理员 | 正常录入阶段 |
| **已结束** | **仅管理员** | 记录人员点「结束本场」后锁定，防误改；管理员可解锁 |
| 已对账 | 仅管理员 | 对账员确认无误后标记；该场数据只读归档 |

> 「结束本场」这个动作很值钱：牌局结束、当场对清、锁定数据，之后谁都不能随手改数字，争议时以锁定值为准。

## 三、场次时段设计（新增）

### 3.1 每天 1~2 场，用「时段」区分

| 场次ID 示例 | 日期 | 时段 | 常见时间 | 记录人 | 桌数 | 状态 |
|---|---|---|---|---|---|---|
| `20261027-PM` | 2026-10-27 | 下午场 | 14:00–17:00 | 张三 | 2 | 已结束 |
| `20261027-NIGHT` | 2026-10-27 | 晚上场 | 19:00–23:00 | 李四 | 3 | 进行中 |

- **场次ID 规则**：`日期-时段码`（PM/NIGHT/自定义简写），天然唯一、可排序
- **时段**做成**可配置字典**（单选字段），默认给「下午场 / 晚上场」，以后想加「早场 / 通宵场」直接在飞书里加选项即可，不用改代码
- 时段可附带**起止时间**（选填），方便对账时知道这场的时长

| 字段 | 类型 | 对应 Excel 列 | 说明 |
|---|---|---|---|

| 本场积分 | 数字 | 本场积分 | **取整后的决算分** |
| **记录人** | 文本 | （新增·审计） | 谁录入的这行 |
| 更新时间 | 日期 | （新增·审计） | 幂等与冲突处理 |

### 表 ④ 角色表 `roles`
| 字段 | 类型 | 说明 |
|---|---|---|
| 昵称 | 文本（主键） | 玩家昵称 |
| 角色 | 单选 | 管理员 / 记录人员 / 对账员 |
| 飞书账号 | 文本 | 选填，升级 OAuth 时填 open_id |
| 备注 | 文本 | 选填 |

> 四张表之间靠「昵称」和「场次ID」两个文本字段关联，**不依赖飞书的关联字段**，好处是可以直接在飞书里肉眼排查、也方便一键导出成 Excel。

### Excel 模板需要同步加 4 列
1. 「玩家昵称」后加 **场次**（`2026-10-27-PM`）
2. 再加 **桌号**（A/B/C）
3. 再加 **记录人**
4. 最后加 **更新时间**

序号 / 签到情况 / 总筹码 / 本场积分 四列保持不变。

## 六、完整业务流程

```
① 管理员建场次
   选日期 + 时段（下午场）+ 桌数(2) + 指定记录人(张三) → 状态「未开始」
        ↓
② 张三（记录人员）用结算页
   选场次 → 填昵称/桌号 → 填筹码 → [添加到本场]
   （云函数校验：当前身份=张三 且 张三是本场记录人 且 场次未锁定）
        ↓
③ 打完一桌切下一桌（A→B），继续录入
        ↓
④ 张三点「结束本场」→ 场次锁定，状态「已结束」
   （此刻总积分/排名已定，页面显示本场最终榜单）
        ↓
⑤ 王五（对账员）打开页面 → 只读查看各场记录与总榜
   → 导出 Excel 与线下账本核对 → 确认无误点「已对账」
        ↓
⑥ 管理员可随时解锁修正（留痕：更新人 + 时间）
```

## 十一、一句话结论

> **最终方案：纯静态网页 + 飞书多维表格（4 张表 = 数据库）+ CloudBase 免费云函数（=安全代理 + 角色校验），现金成本 0 元、开发约 8 人天（精简版 5.5 人天）。**
> 角色分三级：管理员（全权）/ 记录人员（只写自己负责的场次）/ 对账员（只读+导出+对账标记）；
> 每场次指定 1 名记录人，场次按时段区分，结束即锁定。
> 完整链路：建场次 → 指定记录人 → 现场录入（一键写表）→ 结束锁定 → 排名与总榜 → 导出 Excel → 对账确认。
