## 一、现状盘点（决定了方案边界）

| 项目 | 现状 |
|---|---|
| 形态 | 纯静态单页 HTML（无框架、无构建、无后端） |
| 部署 | GitHub Pages（`kuguahahaha.github.io/shuishang`） |
| 存储 | **完全没有**——刷新即清空，不做任何持久化 |
| 计算 | 本地 JS 算完直接显示，昵称仅标记不参与计算 |
| 代码规模 | 单文件约 1200 行（`shuishang.html` 源文件 / `water-club.html` 完整版） |
| 运行环境 | 手机微信内置浏览器为主，桌面浏览器为辅 |
| 网络 | 假设弱网/断网场景存在（线下牌局信号差） |

**关键结论**：当前架构是「零成本、零运维、单人单设备」的最优解。任何"存储 + 多人 + 排名"的需求，都意味着要引入**持久化层**和**共享层**，这必然带来成本与复杂度。本方案的核心任务就是在「成本 / 复杂度 / 体验」三者间取平衡。

## 二、目标功能拆解（从截图推演）

截图下半部分是你现在的 Excel 模板：**「水上俱乐部 · 活动签到与积分记录表」**，字段为：

| 序号 | 玩家昵称 | 签到情况 | 总筹码 | 本场积分 |
|---|---|---|---|---|
| 1 | | | | |

上半部分是当前结算页，箭头指向一个「**添加到表格**」按钮 —— 这就是下一步要打通的链路：

```
结算页（算出一个人的本场结果）
      ↓ 点「添加到表格」
记录表（写入：昵称 / 签到=在场 / 总筹码 / 本场积分）
      ↓
排名结算（按本场积分排本场名次，按累计积分排总榜）
```

因此目标功能可拆为 6 块：

| # | 功能 | 说明 | 复杂度 |
|---|---|---|---|
| F1 | **牌桌/场次管理** | 一桌 = 一个桌号（可命名，如"A 桌"）；一场 = 日期 + 场次序号 | 中 |
| F2 | **签到** | 每个玩家在每场的状态：在场 / 请假 / 缺席 / 迟到 | 中 |
| F3 | **本场记录写入** | 结算页一键把「昵称 + 总筹码 + 本场积分」写入当前场次 | 低 |
| F4 | **本场排名** | 按积分降序，同分并列；显示名次、积分、筹码 | 低 |
| F5 | **累计总榜** | 跨场次累计积分排名（赛季式） | 中 |
| F6 | **数据导入导出** | 与现有 Excel 模板互通；备份与恢复 | 中 |

**贯穿性要求**：
- **离线优先**：牌局现场可能没网，必须能离线记录、联网后同步
- **零丢失**：任何写入都要可导出备份
- **不破坏现有体验**：结算计算逻辑一行不改，单人用还是"填数→出结果"

## 三、数据模型设计

建议的核心表（无论最终用哪种存储，模型先定下来，避免返工）：

```sql
-- 牌桌（一次活动的多个桌）
CREATE TABLE tables (
  id          TEXT PRIMARY KEY,          -- uuid
  name        TEXT NOT NULL,             -- 'A桌' / '主桌'
  session_date TEXT NOT NULL,            -- '2026-10-27'
  session_no  INTEGER NOT NULL DEFAULT 1,-- 第几场
  note        TEXT DEFAULT '',
  created_at  TEXT NOT NULL
);

-- 玩家（昵称主数据）
CREATE TABLE players (
  id          TEXT PRIMARY KEY,
  nickname    TEXT NOT NULL UNIQUE,      -- 昵称唯一，作为业务主键
  alias       TEXT DEFAULT '',           -- 重名时的人工区分后缀
  note        TEXT DEFAULT '',
  created_at  TEXT NOT NULL
);

-- 签到
CREATE TABLE signups (
  id          TEXT PRIMARY KEY,
  table_id    TEXT NOT NULL REFERENCES tables(id),
  player_id   TEXT NOT NULL REFERENCES players(id),
  status      TEXT NOT NULL,             -- 'present' | 'leave' | 'absent' | 'late'
  seat_no     INTEGER,
  UNIQUE(table_id, player_id)
);

-- 本场积分记录（核心）
CREATE TABLE records (
  id           TEXT PRIMARY KEY,
  table_id     TEXT NOT NULL REFERENCES tables(id),
  player_id    TEXT NOT NULL REFERENCES players(id),
  total_chips  INTEGER NOT NULL,         -- 总筹码
  used_cards   INTEGER NOT NULL DEFAULT 0,-- 使用黄卡张数（0~7）
  net_chips    INTEGER NOT NULL,         -- 结算筹码（抵扣后）
  points       REAL NOT NULL,            -- 积分精确值
  final_points INTEGER NOT NULL,         -- 取整后的决算分
  rank         INTEGER,                  -- 本场名次（写入时算）
  remark       TEXT DEFAULT '',
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,
  UNIQUE(table_id, player_id)            -- 同桌同人只一条，重复写入即更新
);
```

**索引建议**：`records(table_id, final_points DESC)` 用于本场排名；`records(player_id)` 用于累计榜。

**昵称唯一性是个坑**（需要在需求里定死）：昵称是业务主键，重复昵称会互相覆盖。三个处理方案：
1. 昵称唯一，重名的人自己改名（最简单）
2. 昵称 + 后缀区分（A/B/张三2）
3. 引入"玩家 ID"（首次录入生成，后续按 ID 认人，昵称只是显示）—— **推荐**，但录入成本略高

## 四、技术选型对比（5 个方案）

| 维度 | 方案A<br>纯前端+本地存储 | 方案B<br>静态站+云端BaaS | 方案C<br>静态站+腾讯文档表格 | 方案D<br>自建轻后端 | 方案E<br>微信小程序+云开发 |
|---|---|---|---|---|---|
| 多人共享 | ❌ 仅本机 | ✅ | ✅ | ✅ | ✅ |
| 离线可用 | ✅ | ✅（读缓存） | ⚠️ 弱 | ⚠️ 弱 | ✅ |
| 实时排名 | 本机即时 | ✅ | ⚠️ 拉表格 | ✅ | ✅ |
| 开发工作量 | **1~2 人天** | 4~6 人天 | 3~5 人天 | 6~9 人天 | 8~12 人天（UI 重做） |
| 月度现金成本 | **0** | 0~30 元 | 0~30 元 | 70~120 元 | 0~30 元 |
| 运维成本 | 0 | 极低 | 低 | 中（要值班） | 低 |
| 部署复杂度 | 现有流程 | 需注册云服务 | 需申请 API 权限 | 需买服务器+域名 | 需注册小程序 |
| 国内访问速度 | — | 视服务商 | 快 | 快 | 最快 |
| 微信内体验 | 一般（分享差） | 一般 | 一般 | 一般 | **最好** |
| 数据自主权 | 本机 | 平台 | 腾讯 | **自有** | 平台 |
| 现有代码复用 | **100%** | 90% | 70% | 90% | 30%（重写 UI） |
| 适合阶段 | **MVP 验证** | **主力方案** | 备选 | 数据量大时 | 长期形态 |

### 方案要点补充

**方案A（本地存储 + Excel 导出）** —— 最快见效
- 浏览器 IndexedDB（或 localStorage）存全部记录
- 「添加到表格」= 写入本地库
- 排名在本地实时算
- 「导出」按钮生成与现有模板同列结构的 `.xlsx`（或 UTF-8 BOM 的 CSV），直接覆盖/追加到 Excel
- 局限：换手机就没了 → 靠导出备份来兜底

**方案B（云端 BaaS）** —— 推荐的主力方案
- 前端仍是静态页（现有 GitHub Pages 部署不变），只多一个 API 层
- 候选：
  - **腾讯云 CloudBase（云开发）**：微信生态原生、国内速度快、免费额度够（数据库 2GB / 云函数 4万次调用每月），Web SDK 简单
  - **Supabase**：开发体验最好（自动生成 REST API + PostgREST + 实时订阅），免费额度 500MB + 5 万 MAU，**但国内直连不稳定**
  - **LeanCloud**：JS SDK 成熟，但绑定自定义域名后配额才正常
- 离线：先写本地队列，联网后增量同步（幂等 upsert + updated_at 冲突解决）

**方案C（腾讯文档/飞书表格即数据库）** —— 零后端但有天花板
- 直接读写共享表格，靠"表格 API"读写行
- 优点：团队协作天然可见，Excel 模板直接复用，不用自己写数据库
- 局限：需申请开放平台权限 + OAuth；行数上限（飞书约 5000 行/表）、写入频率限制、排名查询要全表拉取后本地算；接口随时可能变
- 适合：场次少（< 100 场）、人数少（< 20 人）

**方案D（自建后端）** —— 数据量大或要长期自主时
- Node.js + Express + SQLite（单文件数据库，备份就是复制文件）/ 或 PostgreSQL
- 轻量应用服务器 2核2G 足够，成本约 70~120 元/月；可包年更便宜
- 优点：数据完全自主、无平台锁定、可加复杂权限
- 缺点：要自己处理 HTTPS、备份、监控、安全更新；有运维负担

**方案E（微信小程序 + 云开发）** —— 体验天花板
- 签到、分享、实时排行、消息通知都是小程序原生能力
- 但现有页面 UI 要重做（3D 球球、CSS 渐变等在小程序里要换实现）
- 适合：确认要做多人长期使用后，作为第二形态

## 五、推荐路线（三阶段，每阶段都能独立交付价值）

### 阶段 1：单机记录 + Excel 互通（0 元，1~2 人天）
- 引入 IndexedDB 存储层（表结构照第三节）
- 结算页加「添加到表格」：写入当前场次记录
- 新增「记录表」面板：场次列表、本场排名、累计总榜
- 「导出 Excel」：生成与现有模板完全一致的列结构，UTF-8 BOM CSV 或 xlsx
- 「导入」：支持读取同格式文件回灌（换机恢复）
- **交付物**：单机可用的完整记录 + 排名 + 备份导出；现有计算逻辑零改动

### 阶段 2：云端共享（0~30 元/月，4~6 人天）
- 接入 CloudBase（或 Supabase），表结构不变
- 离线队列 + 联网同步；昵称冲突自动处理
- 多设备/多人同时用：签到、记录、排名实时可见
- 保留「导出 Excel」能力（数据主权在用户手里）
- 可选：微信昵称/头像授权免手填（需小程序或公众号 OAuth，复杂）

### 阶段 3（可选）：小程序形态（0~30 元/月，8~12 人天）
- 把阶段 2 的 API 直接复用，只重做 UI
- 增加：实时排行榜分享卡片、到场提醒、赛事通知

> **阶段 1 的设计必须预留阶段 2 的接口**：存储层做成统一接口（`storage.save/get/list`），本地实现与云端实现可互换，阶段 2 只需替换实现，UI 与业务代码零改动。

## 七、关键技术难点与解法

| 难点 | 解法 |
|---|---|
| **昵称重名覆盖记录** | 引入内部 player_id，昵称仅作显示；或强制昵称唯一 |
| **重复写入（同人同桌写两次）** | `UNIQUE(table_id, player_id)` + upsert 语义，第二次写入即更新 |
| **离线写入与云端冲突** | 以 `updated_at` 时间戳 + 幂等 upsert 解决，后写覆盖；记录表可查看冲突日志 |
| **多端同时签到同一人** | 同上，唯一约束 + 时间戳 |
| **积分口径与现在页面保持一致** | 计算逻辑抽成纯函数 `calcPoints(chips, cards)`，页面与记录模块共用，杜绝两套算法漂移 |
| **Excel 模板兼容** | 导出列名/顺序严格对齐现有模板：序号、玩家昵称、签到情况、总筹码、本场积分；CSV 必须带 UTF-8 BOM，否则 Excel 中文乱码 |
| **排名并列** | 同分同名次（1,1,3），标准竞赛排名 |
| **数据丢失兜底** | 每次写入即本地留存 + 每周导出 Excel；云端开启自动备份 |
| **微信内置浏览器兼容性** | 不使用新特性（`structuredClone`、`:has()`、容器查询等）；IndexedDB 在 X5 内核可用但需降级到 localStorage |

## 八、你要考虑和准备什么（决策清单）

### 8.1 必须先定的 4 个问题
1. **使用规模**：几个人？几个桌？多少场次？是否需要多台设备同时用？
   → 规模 < 10 人 / < 20 场：阶段 1 就够；> 50 人或长期使用：直接上阶段 2
2. **数据存哪**：只在自己手机存（免费、私密）还是团队共享（要云服务）？
3. **是否必须与现有 Excel 模板双向互通**（导入已有历史数据 / 继续用 Excel 发给群友）
4. **是否接受引入外部服务**（实名认证、可能有月费、数据在第三方）

### 8.2 需要你提供/准备的
- [ ] 云服务账号（若选阶段 2/3）：腾讯云实名认证（免费）
- [ ] 历史数据：现有 Excel 里有几场记录？要不要导入？
- [ ] 昵称规则：是否允许重名？是否要"玩家档案"概念
- [ ] 场次定义：一场 = 一天？一天多场怎么编号？"桌"的划分方式
- [ ] 签到状态的完整定义（在场/请假/缺席/迟到/其他）
- [ ] 排名口径：本场排名 + 累计总榜，都要吗？累计总榜按什么周期（季度/年度/滚动）
- [ ] 数据保留策略：多久清一次旧场次？是否需要"软删除"便于追账
- [ ] 成本授权：云服务月费上限（比如 30 元/50 元）由谁承担
- [ ] 是否需要账号登录（决定能否防止他人篡改数据）

### 8.3 我需要预留的技术决策
- 存储抽象层接口（阶段 1/2 可互换实现）
- 计算逻辑单一数据源（页面与记录模块共用）
- 导出格式以现有 Excel 模板为准（先冻结模板列结构）
- 隐私最小化：只存昵称，不存手机号/微信等身份信息（除非明确需要）
