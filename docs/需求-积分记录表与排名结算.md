## 一、目标

把现在的筹码计算工具扩展成 **「逐人录入 → 自动排名 → 自动核对筹码差额 → 导出整表截图」** 一条龙。
**不使用数据库**，数据存本机（localStorage），靠导出文件流转。

**核心诉求**
1. 记录：玩家昵称、本场积分、总码量
2. 排名：按**总码量**降序取前三名
3. 核对：筹码差额 **≤ 3 万**（只管正差额）
4. 交互：**逐个录入**，一次一人，按钮是「录入下一位」「结束录入」，避免看错行
5. 产出：整张表能**截图**，并导出 Excel
6. 人数自由设定；每场（桌）一张独立记录表

## 二、核心概念

| 术语 | 定义 |
|---|---|
| **初始码** | 每人每场 **16 万** = 7 张黄卡（14 万）+ **2 万筹码（送的）** |
| **黄卡** | 每人初始 7 张，1 张 = 2 万筹码 = 10 积分 = 10 元 |
| **剩余黄卡** | 牌局结束时手里还剩几张（录入项之一） |
| **桌面筹码** | 桌上现有的实际筹码（用现有计算器录入） |
| **总码量 C** | **桌面筹码 + 剩余黄卡 × 20000**（纸表「总码量」列填的就是它） |
| **欠卡数 K** | 为还清 7 张黄卡（14 万）需要补买的黄卡数 |
| **支付金额** | K × 10 元 |
| **剩余筹码** | C + K×20000 − 140000（买卡补齐后扣掉 14 万黄卡债务） |
| **本场积分** | floor(剩余筹码 ÷ 2000)；**总码量为 0 时强制 −68**（积分复活，既往不咎） |
| **筹码差额** | Σ各人总码量 − 160000 × **应到人数**，> 30000 告警 |

## 三、计算规则（★ 已用纸表 9 人数据全量验证，9/9 吻合）

### 3.1 结算公式

```
K        = max(0, ceil((140000 − C) ÷ 20000))     欠几张卡
支付金额  = K × 10 元
剩余筹码  = C + K×20000 − 140000                  买卡补齐后扣掉 14 万黄卡债务
本场积分  = floor(剩余筹码 ÷ 2000)                剩余筹码折分（不含支付额）
           ※ C = 0 时强制记 −68（积分复活）
```

### 3.2 三个案例的口述还原（用户原话）

| 昵称 | 总码量 | 口述 | 还原 |
|---|---|---|---|
| 陈锋 | 50000 | 「要还掉 3 张卡…要还回去 6 万，还剩 10000，就是 5 分」 | 欠 5 张卡 → 付 ¥50 → 买卡后 15 万 → 减 14 万 → 剩 1 万 = **5 分** |
| Aaron | 106000 | 「要还 14 万，140000−106000=34000，2 张卡，20 元所以支付 20…还完以后还有 6000 筹码，等于 3 积分」 | 欠 2 张卡 → 付 ¥20 → 剩 6000 = **3 分** |
| Freecat | 112000 | 「112000 一样的道理…140000−112000=28000，40000−28000=12000，6 积分」 | 欠 2 张卡 → 付 ¥20 → 剩 12000 = **6 分** |

| nuy | 150000 | 0 | ¥0 | 10000 | **+5** | +5 | ✅ |

**9 / 9 吻合** ✅　Σ总码量 = 1612000 → 差额 = 1612000 − 1600000 = **12000**（≤3 万 ✅）

### 3.4 排名
按**总码量 C 降序**取前三名（纸表：第一名 somuns 462000 / 第二名 辉 258000 / 第三名 Today 244000 ✅）

### 3.5 筹码差额
```
筹码差额 = Σ各人总码量 − 160000 × 应到人数
判定：差额 > 30000 才告警（只管正差额，负差额不提示）
```

## 五、交互流程

```
① 新建场次：日期 / 场次 / 桌号 / 应到人数（默认 10）
      ↓
② 录入模式：屏幕只显示【当前这一位】
   ┌────────────────────────────────────┐
   │  第 3 位                           │
   │  昵称 [__________]                 │
   │  桌面筹码（7 个面额，实时合计）     │
   │  剩余黄卡 [__] 张                  │
   │  ──────────────────────────────    │
   │  总码量 240000 ｜ 积分 50 ｜ 支付 ¥0 │
   │  [ 录入下一位 ]   [ 结束录入 ]      │
   └────────────────────────────────────┘
      ↓ 点「录入下一位」→ 写入一行 + 下方表格实时追加 + 立即显示下一位
      ↓ 点「结束录入」→ 生成结算面板
      ↓
③ 结算面板
   · 记录表（场次信息 + 序号/昵称/本场积分/总码量 + 三名 🏆）
   · 筹码差额：Σ总码量 − 16w×应到人数 = X（>3万 红色告警）
   · 支付合计：¥Y
   · [ 导出 Excel ] [ 截图 ] [ 复制表格文本 ]
```

### 防看错设计
| 措施 | 说明 |
|---|---|
| 一次只显示一位 | 录入区只有当前玩家，避免左右串行 |
| 实时显示三个结果 | 总码量 / 本场积分 / 支付金额当场算出，录完再确认 |
| 「录入下一位」独立按钮 | 录完一个才提交，Enter 键同效 |
| 表格实时追加 | 录错立刻能看到，可删除/重录 |
| 「结束录入」才出结算 | 避免半成品被当成结果 |
| 结算前二次确认 | 弹出前提示"已录 N 人，还差 M 人（应到 X 人）" |

## 十一、阶段 2 · 云端备份（飞书多维表格）需求

> 详细设计见 `docs/技术方案-飞书云端备份同步.md`（v1.1）。本节只写**需求口径与已确认结论**。

### 11.1 目标
本地保存照旧，**同时**把每条记录备份到用户的飞书多维表格；全程对使用者无感。

### 11.2 已确认结论

| # | 决策 | 结论 |
|---|---|---|
| C1 | 飞书账号 | **个人版飞书**（可建自建应用拿凭据，本场景够用） |
| C2 | 飞书表结构 | 4 张表：场次表 / 积分记录表 / 设备表 / 同步日志表 |
| C3 | 鉴权方式 | **统一口令**（私下分发，首次输入一次）—— 不用逐设备人工审核 |
| C4 | 口令怎么存 | 前端只存 **SHA-256 哈希**（明文输入后即丢弃）；云端也只存哈希 |
| C5 | 改口令 | 在飞书「设备表」改「当前口令哈希」一行 → 全员下次请求被拒、重新输新口令 |
| C6 | 设备标识 | deviceId 降级为**审计与单独停用**（谁写的、停某人），不再作为准入门槛 |
| C7 | 使用者 | **牌友各自录**（每人自己手机），用户统一在飞书汇总 |
| C8 | 数据归属 | 按 **日期 + 场次 + 桌号** 分组；唯一键 = 日期+场次+桌号+昵称（upsert 去重） |
| C9 | 兜底通道 | 手动粘贴 + 导出 CSV 永久保留，云端异常不阻塞现场算账 |
| C10 | 成本 | **0 元/月**（飞书个人版 + CloudBase 免费额度，年调用约 2.4 万次 = 免费额度的 2%） |

### 11.3 关键架构约束（不可妥协）

```
Record.html
  ├─ localStorage   ← 主数据源（即时、离线可用，界面只读它）
  └─ 待同步队列 → CloudBase 云函数（★飞书凭据只存在这里）→ 飞书多维表格
```

| 约束 | 原因 |
|---|---|
| **飞书 app_secret 绝不能进前端** | 浏览器里的 JS 任何人都能 F12 看到 → 凭据泄露 = 别人可读写/清空你的表格。**托管在哪都不影响这一点**（GitHub Pages / CloudBase 静态站 / 自建服务器都一样） |
| 必须有服务端中转 | 飞书开放 API 不支持浏览器直连（跨域限制） |
| 同步必须异步、失败不阻塞 | 弱网/断网/飞书限流时，本地算账照常进行 |
| 幂等 upsert | 重复推送不产生重复行 |

### 11.4 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 凭据进前端 | 🔴 极高 | 只存云函数环境变量 |
| 陌生人往表里灌数据 | 🟠 高 | 统一口令 + deviceId 可单独停用 + 限流（30 次/分、500 场/天）+ 字段校验 |
| 口令在群里扩散 | 🟡 中 | 定期换口令（改一行即可全员失效）+ 可停用单个设备 |
| 昵称隐私泄露 | 🟡 中 | 表格仅用户可编辑；只存昵称不存手机号 |
| 飞书限流/改版 | 🟡 中 | 本地为主 + 队列重试；同步挂了不影响使用 |
| 数据冲突 | 🟡 中 | 唯一键 + updatedAt 最后写入者胜；本地永远留副本 |
| 免费额度政策变化 | 🟢 低 | 本地功能不受影响 |

### 11.5 同步行为规范

| 场景 | 行为 |
|---|---|
| 录入中 | 写入本地 + 入队，**界面不显示任何同步字样**（见 §12.3） |
| 后台 | 每 5 秒 / 页面空闲时批量推送；失败指数退避（1s→2s→4s…最长 5 分钟），最多 20 次 |
| 页面关闭 | sendBeacon 冲刷一次（不保证成功，靠下次打开补传） |
| 断网 | 队列堆积，联网后自动按序补传；队列上限 500 条 |
| 结束录入后 | 在结算面板底部展示一行备份状态（仅此时可见） |

## 十二、新增需求（v3.0）

### 12.1 N1 · 角色与可见范围

> 「管理员可以看到全部的信息，普通用户只能看自己录入的数据」

**先说结论：默认不需要分两个页面。**

| 方案 | 做法 | 成本 | 建议 |
|---|---|---|---|
| **A. 同一页面按角色渲染**（推荐） | 角色只影响「场次列表」这一块：普通用户只列自己录的，管理员列全部。结算/录入/导出逻辑完全共用 | 0 | ✅ |
| B. 两个独立页面 | admin.html + record.html，两套代码两套 UI，后续改一处要改两处 | +1~2 人天 | ❌ 不划算 |
| C. 不做页面级权限 | 网页只管自己录的，「全部」由飞书表格承担（本来就是在那儿汇总） | 0 | ✅ 最省 |

**推荐 A + C 组合**：网页内按角色过滤场次列表（管理员多看到一个「全部场次」入口），而「真正的全局汇总」放在飞书表格里——那里本来就是全部数据、还能多维筛选。

### 12.2 N2 · 角色怎么定

角色**不需要登录系统**，绑定期一次性确定：

| 角色 | 获得方式 | 能看到 |
|---|---|---|
| 普通用户 | 输入团队口令 | 只看自己录入的场次 |
| 管理员 | 团队口令正确 **+** 额外的管理员密钥（单独的管理口令） | 全部场次 + 设备表管理 + 改口令 |

- 管理员密钥用**另一个独立口令**（在飞书表里单独存一条哈希），这样普通牌友拿到的口令只能录自己的
- 管理员视角可做：查看全部场次、停用某台设备、改团队口令、导出全局汇总

### 12.3 N3 · 界面无感要求（重要）

> 「同步这类字眼都不要出现，放在结束录入后再展示计算出来的结果」

**录入过程中完全不出现任何同步相关字样。**

| 位置 | 禁止出现 | 允许出现 |
|---|---|---|
| 顶部标题栏 | ❌ 已同步 / 待同步 N / 同步中… | ❌ 完全不显示同步状态 |
| 录入区 | ❌ 任何同步/上传/云端字样 | ✅ 只有桌面筹码 / 总码量 / 本场积分 / 需支付 |
| 记录表 | ❌ 行级同步标记 | ✅ 只有序号/昵称/积分/总码量/需支付 |
