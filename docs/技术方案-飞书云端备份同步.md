## 〇、先回答你的风险问题（最重要）

### 结论 1：GitHub Pages 本身不是风险源，**「浏览器直接调飞书写入」才是**

| 误解 | 事实 |
|---|---|
| 「托管在 GitHub 上所以有风险」 | ❌ 换成任何静态托管（CloudBase 静态网站、腾讯云 COS、Vercel）都一样——**浏览器里跑的 JS 谁都能看**（F12 就能看到源码）。GitHub Pages 只是让源码更容易被搜到，不是风险本质 |
| 「那放自己服务器就安全了」 | ❌ 前端代码照样公开。**只要凭据在浏览器里，就是公开的** |
| 「所以不能上传」 | ✅ 可以上传——**前提是飞书凭据不进前端** |

### 结论 2：纯静态页 **无法** 安全地直连飞书写入

两个硬性障碍：
1. **凭据泄露**：飞书 `app_secret` / `user_access_token` 写在前端 → 任何访客 F12 就能拿到 → 可读写甚至**清空**你的表格
2. **跨域限制**：飞书开放平台 API 不支持浏览器直连调用，必须有服务端中转

### 结论 3：所以必须加一个「中转」，但它可以是**零成本的免费云函数**

```
浏览器（Record.html）
   ├─ localStorage  ← 主数据源，即时可用、离线可用（现有功能不动）
   └─ 待同步队列（Pending）
          ↓ HTTPS
   CloudBase 云函数  ← ★飞书凭据只存在这里（环境变量），前端永远看不到
          ↓ 飞书开放 API
   飞书多维表格  ← 备份副本
```

> **一句话**：托管在哪不重要，**凭据放哪才重要**。把凭据放进云函数，GitHub Pages 托管就完全没问题。

## 二、架构设计

### 2.1 角色分工：本地为主，云端为辅

| 存储 | 定位 | 特性 |
|---|---|---|
| **localStorage** | **主数据源** | 立即可用、离线可用、零延迟；界面读它，不等网络 |
| **飞书多维表格** | **备份 + 跨设备查看** | 异步写入、可查历史、可多设备只读查看 |
| **CloudBase 云函数** | **安全中转** | 唯一持有飞书凭据；校验 + 限流 + 幂等写入 |

> 原则：**同步永远是异步的、失败不阻塞的**。网络慢、飞书挂了、额度满了——都不影响现场算账，本地照常录，只是「待同步」计数在涨。

### 2.2 无感同步流程

```
① 用户录入一位
   ├─ 写入 localStorage（立即生效，表格刷新）        ← 同步主路
   └─ 把这条记录 push 进 pending 队列
            ↓
② 后台同步器（每 5 秒 / 页面空闲时触发）
   ├─ 取队列中待同步的记录 → 批量 POST 云函数
   ├─ 成功 → 从队列移除
   └─ 失败 → 指数退避重试（1s→2s→4s…最长 5 分钟），最多 20 次
            ↓
③ 页面关闭 / 切后台
   └─ 冲刷一次队列（navigator.sendBeacon 兜底，不保证成功，靠下次打开补传）
            ↓
④ 页面上的极轻量状态指示（不打扰）
   「☁️ 已同步」 / 「☁️ 待同步 3」
```

### 2.3 幂等与冲突
- **唯一键**：`场次ID + 昵称 + 桌号`
- 云函数用 **upsert**（有则更新、无则新增）→ 重复推送不会产生重复行
- **冲突策略**：比较 `updatedAt`，**最后写入者胜**；本地副本始终保留，不会因云端覆盖而丢
- 手工改过的行打 `manual: true` 标记，同步时以本地为准（避免被旧数据覆盖）

### 2.4 离线优先
- 断网时队列持续堆积，页面顶部显示「⚠️ 离线，N 条待同步」
- 网络恢复后自动补传，**按顺序**重放
- 队列上限 500 条（超出丢弃最旧并告警，防止无限膨胀）

## 三、飞书表结构（4 张表，延续 v4.0 方案）

### 表 ① 场次表 `sessions`
| 字段 | 类型 | 说明 |
|---|---|---|
| 场次ID | 文本（主键） | `20261029-PM-8f3a`（含设备短码，避免多设备撞号） |
| 日期 / 场次 / 桌号 | 文本 | 与本地一致 |
| 应到人数 | 数字 | 差额校验基准 |
| 记录人 / 审核人 / 评分 | 文本 | |
| 来源设备 | 文本 | deviceId 短码，用于溯源 |
| 创建时间 / 更新时间 | 日期时间 | 冲突判定用 |

### 表 ② 积分记录表 `records`
| 字段 | 类型 | 对应本地字段 |
|---|---|---|
| 昵称 | 文本 | `name` |
| 场次ID | 文本 | 关联表① |
| 桌号 | 文本 | `table` |
| 桌面筹码 | 数字 | `chips` |
| 剩余黄卡 | 数字 | `cards` |
| 总码量 | 数字 | `total` |
| 本场积分 | 数字 | `points` |
| 需支付 | 数字 | `pay` |
| 欠卡数 | 数字 | `cardGap` |
| 更新时间 | 日期时间 | 冲突判定 |
| 手工修改 | 复选框 | `manual` |

### 表 ③ 设备白名单 `devices`
| 字段 | 说明 |
|---|---|
| deviceId | 首次进入页面自动生成的 UUID（存本地） |
| 设备备注 | 首次同步时让你填，如「锁舟的手机」 |
| 启用状态 | 启用 / 停用（停用后该设备写入被拒） |
| 首次出现 / 最近出现 | 时间 |
| 累计写入行数 | 统计 |

> **这是 R2 的核心防线**：新设备第一次同步时状态为「待审核」，写入请求被云函数拒绝；你在飞书表里把它改成「启用」后即可正常使用。

### 表 ④ 同步日志 `sync_logs`（可选，出问题时排查用）
时间 / deviceId / 操作（新增·更新·删除）/ 目标场次 / 结果 / 错误信息

## 四、身份识别与授权（"无感"的边界）

要做到真正无感，需要先解决"**这条数据是谁的**"：

| 方案 | 用户操作 | 安全性 | 体验 |
|---|---|---|---|
| **A. deviceId 白名单**（推荐） | 首次进入 → 填一次「设备备注」→ 你在飞书里点「启用」 | 🟢 高 | 一次性 |
| B. 飞书 OAuth 登录 | 首次进入 → 跳转授权 → 自动拿 open_id | 🟢 最高 | 要跳转，打断感强 |
| C. 不做鉴权 | 零操作 | 🔴 谁都能写你的表 | 无感但危险 |

**推荐 A**：第一次使用时弹一个小框让填「这台设备是谁的（如：锁舟的手机）」，之后全自动。你在飞书白名单表里启用即可。玩家（被记录的昵称本人）完全无感知。

## 五、安全加固清单（上线前必做）

| # | 措施 |
|---|---|
| 1 | `app_id` / `app_secret` **只存云函数环境变量**，代码库里不放任何明文 |
| 2 | 前端只持有云函数调用地址 + 临时令牌（可设短时效并轮换） |
| 3 | 云函数强制校验：deviceId 是否在白名单且启用 |
| 4 | 云函数限流：单设备每分钟 ≤ 30 次写入、每天 ≤ 500 场次 |
| 5 | 云函数字段校验：昵称长度 ≤ 12、数值范围、场次人数 ≤ 30，非法直接拒 |
| 6 | 昵称等字段在写入前做转义，防止注入表格公式（`=`、`+` 开头加前缀 `'`） |
| 7 | 飞书表格权限：仅你可编辑；需要的话给牌友「可阅读」 |
| 8 | 云函数日志不打印完整昵称（只打印 hash 前几位） |
| 9 | 本地队列加密？不必要——昵称本身在飞书里也明文；但**设备 ID 用随机 UUID**，不含个人信息 |
| 10 | 提供「暂停同步」开关（设置里一键关掉，便于你怀疑时应急） |

## 八、与现有方案的关系

```
Record.html（阶段1·本地版）  ← 已完成，本地为主
      │
      ├─ + 同步队列（阶段2）  ← 本方案（云端备份，飞书多维表格）
```
